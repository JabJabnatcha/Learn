Master Guide: การวางตำแหน่งโค้ดและเส้นทางข้อมูล (Code Placement & Data Flow)

หัวใจของการออกแบบสถาปัตยกรรม: ไม่ว่าจะเป็น Layered Architecture, Clean Architecture หรือ Hexagonal Architecture คำถามที่วิศวกรซอฟต์แวร์ต้องตอบให้ได้สำหรับโค้ดทุกไฟล์คือ:
"ไฟล์นี้ต้องอยู่ที่ Layer ไหน? รับอะไรเข้ามาจากใคร? ทำงานอะไร? และส่งผลลัพธ์ต่อไปที่ไหน อย่างไร?"

1. คาถา 4 ข้อในการวิเคราะห์โค้ดทุกไฟล์ (The 4 Golden Questions)

1. Where do I live? (ฉันต้องอยู่ที่ Layer ไหน?)

ขึ้นอยู่กับว่าโค้ดนั้นขึ้นตรงกับเทคโนโลยีภายนอก (HTTP/DB) หรือเป็นตรรกะธุรกิจล้วน ๆ

2. What comes in? (รับอะไรเข้ามา และรับจากใคร?)

เป็น HTTP JSON หรือไม่? เป็น DTO? เป็น Domain Entity? หรือเป็น Parameter ธรรมดา?

3. What is my job? (หน้าที่รับผิดชอบของโค้ดนี้คืออะไร?)

ตรวจสอบ HTTP Status? ร้อยเรียง Use Case? บังคับกฎเกณฑ์ธุรกิจ (Business Rules)? หรือส่งคำสั่ง SQL ไปยัง Database?

4. What goes out, to whom, and how? (ส่งผลลัพธ์อะไร ออกไปให้ใคร และอย่างไร?)

ส่งคืน DTO? คืนค่า Entity? ยิง SQL? ส่ง HTTP 200/400? หรือกระจาย Event ลงใน Topic?

2. ตารางแผนผังตำแหน่งโค้ดแม่บท (Master Code Placement Matrix)

ตารางสรุปสำหรับโค้ดทุกประเภทในโปรเจกต์จริง (อ้างอิงจากโซลูชัน MyAwesomeApi ในโปรเจกต์ของคุณ):

ชนิดของโค้ด (Artifact) Layer ที่สังกัด รับอะไร? จากใคร? (Input) ทำงานอะไรข้างใน? (Responsibility) ส่งอะไร? ให้ใคร? อย่างไร? (Output)
Controller / Endpoint
LessonEndpoints.cs		 Presentation รับ HTTP Request (JSON Body, Query Params, Headers) จาก Client / Browser ตรวจสอบ Authentication, ตรวจรูปแบบข้อมูลพื้นฐาน (Validation), ถอดรหัส JSON เป็น DTO เรียก Application Service แล้วแปลงผลลัพธ์เป็น HTTP Response (200 OK / 400 Bad Request) พร้อม JSON กลับไปหา Client
Request / Response DTO
CheckoutRequestDto		 Application / Presentation รับค่าข้อมูลแบน ๆ (Primitive types เช่น string, int, decimal) จาก JSON ขาเข้า เป็นเพียงกระเป๋าใส่ข้อมูล (Data Carrier) ไม่มี Logic ธุรกิจใด ๆ ถูกส่งข้ามพรมแดนจาก Presentation เข้าสู่ Application Service เพื่อไม่ให้ Domain รั่วไหล
Use Case / Service
CheckoutService.cs		 Application รับ Request DTO มาจาก Presentation (Controller) ร้อยเรียงกระบวนการทำงาน (Orchestrator): สั่ง Repository ดึง Entity, เรียก Method ของ Entity เพื่อคิดเงิน, เรียก Payment Gateway, สั่ง Save ส่ง Response DTO กลับไปให้ Controller และสั่ง Interface ต่าง ๆ ในการทำงาน
Domain Entity
Product.cs, BankAccount.cs		 Domain รับคำสั่งและข้อมูลผ่าน Method Call จาก Application Service (เช่น product.DeductStock(qty)) ผู้คุมกฎทางธุรกิจสูงสุด (Business Invariants): คำนวณยอดเงิน, ป้องกันสต็อกติดลบ, จัดการสถานะ (Zero Dependency ห้ามรู้จัก DB หรือ HTTP!) อัปเดต State ภายในตัวเอง หรือคืนค่าผลลัพธ์คำนวณ หรือ Throw Business Exception
Repository Interface
IProductRepository.cs		 Application (หรือ Domain) กำหนดลายเซ็นเมธอดที่ Use Case ต้องการใช้ (เช่น Task<Product> GetByIdAsync(int id)) เป็นเพียง "สัญญาข้อตกลง (Contract)" ไม่มีโค้ดทำงานจริง ทำหน้าที่เป็นตัวตัดขาด Dependency (Inversion of Control) ให้ Infrastructure เป็นคนหยิบไปสวมโค้ดทำงานจริง (Implement)
Repository Implementation
InMemoryProductRepository.cs		 Infrastructure รับคำสั่งจาก Application Service ผ่าน Interface และรับ Domain Entity มาบันทึก ใช้ EF Core, Dapper หรือ SQL ดิบ เพื่อแปลงข้อมูลระหว่าง Table ในฐานข้อมูล กับ Domain Entity ส่งคำสั่ง I/O ไปคุยกับ Database จริง แล้วแปลงข้อมูลที่ได้กลับมาเป็น Domain Entity ส่งคืนให้ Service
External Gateway Adapter
StripeGateway.cs		 Infrastructure รับข้อมูลจำนวนเงินและบัตรเครดิต ผ่านสัญญา IPaymentGateway ที่ Application ส่งมา ติดต่อ Third-Party SDK / ยิง HTTP API ภายนอก เช่น Stripe, PayPal, Twilio ส่งผลลัพธ์สำเร็จ/ล้มเหลว (PaymentResult) กลับคืนให้ Application Service
Middleware / Filter
ApiKeyMiddleware.cs		 Presentation ดักจับ HTTP Request Context ก่อนที่จะถึง Controller ตรวจสอบ Header เช่น X-Api-Key, ดักจับ Exception กลางระบบ, บันทึก Log หากผ่าน ส่งต่อไปยัง Middleware ตัวถัดไป (next(context)) หากไม่ผ่าน คืน HTTP 401 Unauthorized ทันที

3. แผนผังเส้นทางข้อมูลจริงตั้งแต่ต้นจนจบ (End-to-End Walkthrough: Checkout Flow)

ดูภาพการเดินทางของคำสั่ง "สั่งซื้อสินค้า (Checkout)" จากเบราว์เซอร์จนถึงฐานข้อมูล และเดินทางกลับ:

4. กฎเหล็ก 3 ข้อที่ห้ามละเมิดเด็ดขาด (Architectural Invariants)

  • กฎข้อที่ 1 (The Dependency Rule): การอ้างอิงต้องชี้เข้าหาจุดศูนย์กลางเสมอ Domain ห้าม Reference หาใครเลย และ Application ห้าม Reference หา Infrastructure เด็ดขาด
  • กฎข้อที่ 2 (Don't leak Entities to Presentation): อย่าส่ง Domain Entity กลับไปให้ Client ตรง ๆ เพราะจะทำให้โครงสร้างภายในของระบบรั่วไหล และเกิด Over-posting Vulnerability ให้ใช้ DTO กั้นเสมอ
  • กฎข้อที่ 3 (Infrastructure is a Detail): Database, ORM, และ Third-party API เป็นเพียง "รายละเอียดภายนอก" วันใดที่ต้องการเปลี่ยนจาก InMemory เป็น PostgreSQL หรือ SQL Server เราจะแก้แค่ในโฟลเดอร์ Infrastructure โดยที่ Domain และ Application จะไม่สะเทือนเลยแม้แต่บรรทัดเดียว!
