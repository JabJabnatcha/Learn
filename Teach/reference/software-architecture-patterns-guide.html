Software Architecture Patterns Reference Guide

หนังสืออ้างอิง: Software Architecture Patterns (2nd Edition) โดย Mark Richards (O'Reilly Media)
สรุปแก่นสาระสำคัญ คู่มือการตัดสินใจเลือกสถาปัตยกรรม และตารางวิเคราะห์เปรียบเทียบ (Trade-off Matrix) อย่างครบถ้วน

1. ลำดับชั้นแนวคิดสถาปัตยกรรม (Conceptual Hierarchy)

หลายคนมักสับสนระหว่าง Architecture Style, Architecture Pattern และ Design Pattern ในหนังสือเล่มนี้ Mark Richards ได้จัดลำดับชั้นไว้อย่างชัดเจน:

Developers often confuse Architecture Style, Architecture Pattern, and Design Pattern. Mark Richards clarifies the hierarchical relationship:

┌────────────────────────────────────────────────────────────────────────┐ │ 1. Architecture Style (Macro Structure: ภาพรวมระดับระบบ) │ │ เช่น Layered, Microservices, Event-Driven, Microkernel, Space-Based │ └───────────────────────────────────┬────────────────────────────────────┘ │ ประกอบด้วย (composed of) ▼ ┌────────────────────────────────────────────────────────────────────────┐ │ 2. Architecture Pattern (Structural Building Blocks: บล็อกแก้ปัญหาระบบ) │ │ เช่น CQRS, Saga Pattern, Event Sourcing, API Gateway │ └───────────────────────────────────┬────────────────────────────────────┘ │ นำไปสร้างด้วย (implemented with) ▼ ┌────────────────────────────────────────────────────────────────────────┐ │ 3. Design Pattern (Code-Level Design: การออกแบบโค้ดระดับ Class/Object) │ │ เช่น Factory, Strategy, Builder, Observer, Decorator │ └────────────────────────────────────────────────────────────────────────┘
  • The Big Ball of Mud Anti-Pattern: การเริ่มเขียนโค้ดโดยไม่มีสถาปัตยกรรมรองรับ จะทำให้โค้ดพันกันยุ่งเหยิง (Tightly coupled) เปราะบาง (Brittle) แก้จุดหนึ่งพังอีกจุดหนึ่ง และไม่มีทิศทางที่ชัดเจน

2. สองมิติหลักในการจำแนกสถาปัตยกรรม (Classification & Partitioning)

มิติที่ 1: Monolithic vs Distributed

Monolithic (หน่วยติดตั้งเดียว): ง่าย ต้นทุนต่ำ (Low cost) พัฒนารวดเร็ว แต่ Scale แยกส่วนไม่ได้ และหากจุดใด Memory Leak ทั้งระบบจะล่ม (Single Point of Failure)

Distributed (หลายหน่วยติดตั้ง/Services): ปรับขนาดแยกอิสระ (Elasticity/Scalability), ความทนทานต่อข้อผิดพลาดสูง (Fault Tolerance) แต่ต้องเผชิญกับ 8 Fallacies of Distributed Computing (เครือข่ายไม่ได้เสถียร 100%, มี Latency, ต้องจัดการ Eventual Consistency และ Distributed Transactions)

มิติที่ 2: Technical vs Domain Partitioning

Technical Partitioning: แยกโค้ดตามหน้าที่ทางเทคนิค เช่น UI, Business Logic, Persistence, Database (เช่น Layered, Space-Based) เหมาะเมื่อทีมงานถูกจัดตามทักษะ (ทีม Frontend, ทีม Backend, ทีม DBA)

Domain Partitioning: แยกโค้ดตามขอบเขตธุรกิจ เช่น Customer, Payment, Shipping (เช่น Microservices) เหมาะกับทีม Cross-functional และทำให้เพิ่มฟีเจอร์ใหม่ได้คล่องตัวโดยกระทบจุดเดียว (High Agility)

3. เจาะลึก 5 รูปแบบสถาปัตยกรรมหลัก (The 5 Architecture Styles)

Monolithic Technical Partitioned

1. Layered Architecture (สถาปัตยกรรมแบบแบ่งชั้น / n-tier)

สถาปัตยกรรมดั้งเดิมที่ได้รับความนิยมสูงสุด แบ่งระบบออกเป็นชั้นแนวนอนตามบทบาทหน้าที่ มาตรฐานมักมี 4 ชั้น: Presentation → Business → Persistence → Database

The de facto standard architecture style. Components are organized into horizontal technical layers, typically: Presentation, Business, Persistence, and Database.

[Presentation Layer] (UI, View, Controller) │ ▼ (Closed Layer: บังคับผ่านเสมอ) [ Business Layer ] (Domain Logic, Calculations, Rules) │ ▼ (Closed Layer) [Persistence Layer ] (DAOs, Repositories, ORM, SQL) │ ▼ [ Database Layer ] (Tables, Stored Procedures)
Key Concept — Layers of Isolation & Open/Closed Layers:
• Closed Layer: คำขอต้องผ่านชั้นนี้เสมอ ห้ามข้าม เพื่อป้องกันการผูกมัด (Decoupling) เช่น ถ้าเปลี่ยน Database หรือ Presentation โค้ดส่วน Business จะไม่ได้รับผลกระทบ
• Open Layer: อนุญาตให้คำขอลัดข้ามชั้นนี้ได้ เช่น Shared Services Layer ที่สร้างไว้ให้ Business เรียกใช้ แต่ถ้าไม่มีการคำนวณก็อนุญาตให้ทะลุไปหา Persistence ได้ทันที
• Architecture Sinkhole Anti-Pattern: สภาวะที่คำขอ 80%+ ไหลผ่านชั้นต่างๆ โดยไม่มี Business Logic ใดๆ (แค่ส่งต่อเฉยๆ) หากพบปัญหานี้ ควรพิจารณาเปิด Layer (Open Layer) หรือปรับสถาปัตยกรรม

✅ เมื่อไรที่ควรเลือกใช้ (When to Consider)

  • งบประมาณและเวลามีจำกัด (Budget & Time constraints)
  • แอปพลิเคชันเริ่มต้นที่ยังไม่ซับซ้อน (Good general-purpose starting point)
  • การเปลี่ยนแปลงส่วนใหญ่จำกัดอยู่ในชั้นทางเทคนิคเฉพาะจุด
  • โครงสร้างทีมแบ่งตามความเชี่ยวชาญเทคนิค (Conway's Law)

❌ เมื่อไรที่ไม่ควรเลือกใช้ (When NOT to Consider)

  • ต้องการ High Scalability, Fault Tolerance, และ Elasticity สูง
  • การเปลี่ยนแปลงส่วนใหญ่เป็นแบบข้ามสายงานตามฟีเจอร์ธุรกิจ (Domain changes)
  • โครงสร้างทีมเป็นทีม Cross-functional ตาม Domain
Monolithic (ส่วนใหญ่) หรือ Distributed Domain หรือ Technical Partitioned

2. Microkernel Architecture (สถาปัตยกรรมแบบปลั๊กอิน / Plug-in)

ประกอบด้วย 2 ส่วนหลักคือ Core System (ระบบแกนกลางที่ทำงานพื้นฐาน) และ Plug-in Modules (โมดูลเสริมที่เพิ่มความสามารถหรือกฎเฉพาะทาง) เชื่อมต่อกันผ่าน Plug-in Registry และ Contract Interfaces

Consists of a minimal Core System and independent Plug-in Modules that extend functionality without modifying the core.

┌──────────────────┐ │ Plug-in Registry │ └────────┬─────────┘ │ ┌─────────────────────────────▼───────────────────────────────┐ │ Core System │ │ (Minimal Business Workflow / Routing / Common Infrastructure)│ └──────────────┬──────────────┬──────────────┬────────────────┘ │ │ │ ┌──────▼──────┐┌──────▼──────┐┌──────▼──────┐ │ Plug-in A ││ Plug-in B ││ Plug-in C │ │(California) ││ (Texas) ││ (Florida) │ └─────────────┘└─────────────┘└─────────────┘
Key Concept — Plug-in Independence & Extensibility:
• ปลั๊กอินต้องเป็นอิสระต่อกัน (Independent) ไม่ควรเรียกหากันเองโดยตรง เพื่อไม่ให้เกิดวงจร Dependency
• ตัวอย่างคลาสสิก: Eclipse IDE, VS Code, Web Browsers (Chrome Extensions)
• ตัวอย่างงานธุรกิจจริง: ระบบเคลมประกันภัย (Insurance Claims Processing) ที่แกนกลางมีขั้นตอนการเคลมมาตรฐาน แต่แต่ละรัฐ/ประเทศมีข้อบังคับต่างกัน จึงแยกข้อบังคับแต่ละรัฐออกเป็นแต่ละ Plug-in!

✅ เมื่อไรที่ควรเลือกใช้

  • ซอฟต์แวร์ประเภท Product-based หรือ SaaS ที่ต้องมี Release หลายเวอร์ชัน
  • ระบบที่มีฟีเจอร์เฉพาะตามกลุ่มลูกค้าหรือตามพื้นที่ (Jurisdictions/Tenants)
  • ต้องการเพิ่ม/ถอดฟีเจอร์ได้อย่างรวดเร็วโดยไม่กระทบระบบแกนกลาง

❌ เมื่อไรที่ไม่ควรเลือกใช้

  • ระบบที่ต้องการ Extreme Scalability หรือ Distributed Data เป็นหลัก
  • การทำงานร่วมกันระหว่างปลั๊กอินมีความซับซ้อนและผูกพันกันสูง
Distributed Technical Partitioned

3. Event-Driven Architecture (สถาปัตยกรรมขับเคลื่อนด้วยเหตุการณ์ / EDA)

สถาปัตยกรรมแบบกระจายศูนย์ที่อาศัยการสื่อสารแบบ Asynchronous ที่แยกตัวกันอย่างสมบูรณ์ (Highly Decoupled) โดย Services จะคอยส่งสัญญาณเหตุการณ์ (Events) และตอบสนองต่อเหตุการณ์ที่เกิดขึ้น

A distributed architecture style relying on asynchronous communication between highly decoupled event processors reacting to events.

[Initiating Event] (เช่น "Place Order") │ ▼ [Order Placement Service] ──(Advertises)──► [Event: "Order Placed"] (Topic) │ ┌─────────────────────────────┼─────────────────────────────┐ ▼ ▼ ▼ [Payment Service] [Inventory Service] [Notification Service] │ │ │ ▼ ▼ ▼ [Event: Payment Applied] [Event: Inventory Reserved] [Event: Customer Notified]
Key Distinction — Event-Driven vs. Message-Driven:
• Event: บอกถึงสิ่งที่ "เกิดขึ้นแล้ว" (State change) เช่น "Order Placed" ผู้ส่งไม่รู้และไม่สนใจว่าใครจะมารับฟังบ้าง ผู้ส่งเป็นเจ้าของ Channel และ Contract
• Message: เป็น "คำสั่ง" (Command) ที่เจาะจงผู้รับ เช่น "Apply Payment" ส่งตรงไปยัง Payment Service ผู้รับเป็นเจ้าของ Queue และ Contract
• Architectural Extensibility: การให้ Service ประกาศเหตุการณ์เสมอ (แม้ ณ ปัจจุบันจะยังไม่มีใครฟัง) จะเปิดช่องทาง (Hook) ให้บริการใหม่ๆ ในอนาคตเข้ามาเสียบฟังได้ทันทีโดยไม่ต้องแก้โค้ดเก่าเลย!

✅ เมื่อไรที่ควรเลือกใช้

  • ต้องการ Scalability, Fault Tolerance และ Performance ระดับสูงสุด (5 ดาว)
  • ระบบที่มี Workflow ซับซ้อนแบบ Dynamic / Non-deterministic
  • ต้องการ Real-time streaming, การตอบสนองรวดเร็ว และ Loose Coupling

❌ เมื่อไรที่ไม่ควรเลือกใช้

  • ระบบที่ต้องการ Deterministic Workflow สูง (ขั้นตอน 1 → 2 → 3 ต้องเป๊ะ)
  • ต้องการระบบ ACID Transaction แบบเข้มงวด (EDA ใช้ Eventual Consistency)
  • ทีมมีข้อจำกัดเรื่องทักษะการดีบักและการติดตามข้อผิดพลาดข้ามระบบ (Error handling)
Distributed Domain Partitioned

4. Microservices Architecture (สถาปัตยกรรมไมโครเซอร์วิส)

ระบบนิเวศของบริการขนาดเล็กที่แยกการติดตั้งเป็นอิสระต่อกัน (Separately deployed) แต่ละบริการทำงานเฉพาะทางเพียงอย่างเดียวให้ดีที่สุด (Single-purpose unit) และมี Bounded Context ของตัวเองทั้งโค้ดและข้อมูล

An ecosystem of single-purpose, separately deployed software units. The key defining characteristics are Bounded Context and Distributed Data.

[ Client Request / Microfrontends ] │ ▼ [ API Gateway ] (Security, Metrics, Routing — NO Business Logic!) │ ┌─────────────────┼─────────────────┐ ▼ ▼ ▼ ┌───────────────┐ ┌───────────────┐ ┌───────────────┐ │ Order Service │ │Customer Service│ │Payment Service│ <-- Bounded Contexts └───────┬───────┘ └───────┬───────┘ └───────┬───────┘ │ │ │ ▼ ▼ ▼ [(Order DB)] [(Customer DB)] [(Payment DB)] <-- Distributed Data
3 สิ่งที่ทำให้ Microservices แตกต่างจากสถาปัตยกรรมอื่น:
1. Distributed Data (ข้อมูลกระจายตัว): เป็นสถาปัตยกรรมเดียวที่บังคับให้แยก Schema/Database ตาม Bounded Context ห้ามแชร์ฐานข้อมูลรวมกันเด็ดขาด (เพราะถ้ามี 200 เซอร์วิสใช้ DB เดียวกัน เมื่อเปลี่ยน Table ทีเดียว จะต้องแก้และ Deploy ทั้ง 200 เซอร์วิสพร้อมกัน!)
2. Operational Automation: ต้องอาศัย CI/CD, Containerization, Automated Testing และ Monitoring ระดับสูงมาก
3. Organizational Change: สอดคล้องกับทีมพัฒนาที่เป็น Cross-functional Domain Teams

✅ เมื่อไรที่ควรเลือกใช้

  • ต้องการ Agility สูงสุด (5 ดาว): ปรับเปลี่ยนและ Deploy ฟีเจอร์ได้เร็วที่สุดโดยไม่กระทบส่วนอื่น
  • ระบบขนาดใหญ่ที่มีหลายโดเมนธุรกิจอิสระจากกัน
  • ต้องการ High Scalability และ Fault Tolerance ระดับรายเซอร์วิส

❌ เมื่อไรที่ไม่ควรเลือกใช้

  • ระบบขนาดเล็กหรืองบประมาณต่ำ (Overall Cost สูงสุดระดับ $$$$$)
  • โครงสร้างพื้นฐานหรือทีมยังไม่พร้อมรับมือความซับซ้อนของระบบกระจายศูนย์
  • ต้องการ Performance แบบ Low-latency สุดขีด (Network hops ระหว่างบริการจะเพิ่ม latency)
Distributed Technical Partitioned

5. Space-Based Architecture (สถาปัตยกรรมเชิงพื้นที่ข้อมูลในหน่วยความจำ)

ออกแบบมาเพื่อทลาย "คอขวดของฐานข้อมูล (Database Bottleneck)" โดยการนำ Database ออกจากกระบวนการ Transactional ปกติ แล้วเปลี่ยนมาเก็บและประมวลผลข้อมูลใน In-Memory Data Grid แทน!

Designed to address extreme scalability and concurrency by eliminating the central database from transactional processing, using replicated in-memory data grids.

[ Requests ] ──► [ Messaging Grid ] (Load Balancer / Session Router) │ ┌───────────────────────────┴───────────────────────────┐ ▼ ▼ ┌─────────────────────────┐ ┌─────────────────────────┐ │ Processing Unit 1 │ │ Processing Unit 2 │ │ ┌─────────────────────┐ │ │ ┌─────────────────────┐ │ │ │ Business Logic │ │ │ │ Business Logic │ │ │ ├─────────────────────┤ │◄──── Data Replication ────►│ ├─────────────────────┤ │ │ │ In-Memory Data Grid │ │ │ │ In-Memory Data Grid │ │ │ └──────────┬──────────┘ │ │ └──────────┬──────────┘ │ └────────────┼────────────┘ └────────────┼────────────┘ │ (Asynchronous Data Pump) │ └───────────────────────────┬───────────────────────────┘ ▼ [ Data Writer ] │ ▼ [ Central Database ]
Key Concept — Virtualized Middleware 4 ส่วน:
• Messaging Grid: จัดการกระจายคำขอไปยัง Processing Unit ที่พร้อมทำงาน
• Data Grid: ซิงค์ข้อมูลระหว่าง Processing Units ให้ตรงกันในแรม (Hazelcast, Apache Ignite) พร้อม Data Pump ส่งข้อมูลแบบ Asynchronous ลง Database ผ่าน Data Writer
• Processing Grid: ดูแลการประมวลผลข้าม Processing Unit
• Deployment Manager: ตรวจสอบโหลด และสั่ง Auto-scale ปิด/เปิด Processing Units แบบไดนามิก (Kubernetes)

✅ เมื่อไรที่ควรเลือกใช้

  • Extreme Scalability & Concurrency: ผู้ใช้ระดับแสนหรือล้านคนพร้อมกัน (เช่น เว็บจองตั๋วคอนเสิร์ต, ระบบประมูลออนไลน์, ตลาดหลักทรัพย์)
  • ต้องการ High Performance และ Elasticity สูงสุด ตอบสนองในระดับ Milliseconds

❌ เมื่อไรที่ไม่ควรเลือกใช้

  • ปริมาณข้อมูล Transactional มหาศาลจนไม่สามารถเก็บในหน่วยความจำ (RAM) ได้
  • ระบบที่มีงบประมาณจำกัด (ต้นทุนโครงสร้างพื้นฐาน RAM และคลัสเตอร์สูงมาก $$$$$)
  • ระบบที่มีการทำ Distributed Transaction ซับซ้อนข้ามหลายตาราง
