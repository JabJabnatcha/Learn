📋 Project Brief

Build a .NET Web API for a company's HR department. The system manages three types of employees and exposes a REST API that a Vue.js frontend can consume.

🏢 Business Requirements
  • The company has three employee types: Full-Time, Part-Time, and Contractor.
  • Each type calculates salary differently.
  • HR can list all employees, get one by ID, and add a new employee.
  • The system must be testable — business logic must not depend on the database.
  • The system must follow Clean Architecture layer separation.
  • Frontend (Vue.js) must be able to call the API from a different origin (CORS).

Domain Models — Employee Hierarchy
L1 · L2 · L3 · L4 ~20 min

🎯 What to Build

  • Create the Domain layer of your project.
  • Design a base class (or abstract class) called Employee that holds shared data: Id, Name, Department, and HireDate.
  • Create three derived classes: FullTimeEmployee, PartTimeEmployee, ContractEmployee.
  • Each derived class must override a method CalculateMonthlySalary() with different logic:
    • FullTime: fixed monthly salary (stored as a field).
    • PartTime: hourly rate × hours worked per month.
    • Contract: daily rate × working days in month.
  • The Employee base must declare CalculateMonthlySalary() as a method that subclasses must implement — choose the right C# keyword.

Knowledge to use:

L1 — Classes & Objects · L2 — Encapsulation & Properties · L3 — Inheritance & Polymorphism · L4 — Abstract Classes
💡 Hints (try without first)
  • Think: should Employee be instantiated directly? That should guide your choice between abstract class and a regular class.
  • Use L3 knowledge to pick the right keyword that forces subclasses to override a method.
  • Properties vs public fields — revisit L2 to decide which is more appropriate for domain models.
Level Criterion
🟡 Beginner Classes exist and inherit from Employee. CalculateMonthlySalary() exists on all three, but may use public fields instead of properties.
🟢 Competent Employee is abstract. Properties used correctly. Override keyword used on all subclasses. Salary logic is per-type.
🔵 Proficient Can explain why abstract is chosen over interface here. Properties have correct access modifiers. No logic in the base class for salary.

Define Interfaces (SOLID-compliant)
L4 · L6 · L7 ~15 min

🎯 What to Build

  • In the Application layer, define two focused interfaces (not one fat one):
  • IEmployeeRepository — declares data access operations: GetAll, GetById, Add.
  • IEmployeeService — declares business operations: GetAllEmployees, GetEmployee, AddEmployee.
  • Each interface should have only the methods relevant to its single responsibility.

Knowledge to use:

L4 — Interfaces · L6 — SRP & OCP · L7 — ISP & DIP
💡 Hints (try without first)
  • Interface Segregation (L7): would a class that only needs to read employees need to know about Add? Split accordingly.
  • Dependency Inversion (L7): the service should depend on the repository interface, not a concrete class.
  • Interfaces live in Application layer because they define what not how.
LevelCriterion
🟡 BeginnerTwo interfaces exist with some methods. May have too many methods in one interface.
🟢 CompetentInterfaces are focused. IEmployeeRepository only has data methods. IEmployeeService only has business methods.
🔵 ProficientCan articulate which SOLID principles each interface decision satisfies, and why they're in Application not Domain.

Application Layer — EmployeeService
L7 · L11 ~15 min

🎯 What to Build

  • Create EmployeeService in the Application layer that implements IEmployeeService.
  • It must receive its IEmployeeRepository dependency through the constructor — not by creating it internally.
  • Implement all methods. Business rules:
    • GetAllEmployees() — returns all employees from the repository.
    • GetEmployee(id) — returns a single employee or throws a meaningful exception if not found.
    • AddEmployee(employee) — validates that Name is not empty before adding. Throw if invalid.

Knowledge to use:

L7 — DIP · L11 — Clean Architecture layers
💡 Hints (try without first)
  • Constructor injection is the DIP pattern from L7 — the class shouldn't create its own dependencies.
  • The service doesn't know how data is stored — that's Infrastructure's job (L11).
  • Throwing exceptions from business rules is perfectly acceptable at this layer.
LevelCriterion
🟡 BeginnerEmployeeService exists and calls the repository. Dependency may be created with new inside the class.
🟢 CompetentDependency injected via constructor. All methods implemented. Name validation present.
🔵 ProficientNo Infrastructure imports in Application layer. Can explain why creating IEmployeeRepository with new inside the service would violate DIP.

Infrastructure — In-Memory Repository
L12 ~15 min

🎯 What to Build

  • Create InMemoryEmployeeRepository in the Infrastructure layer.
  • It must implement IEmployeeRepository from Application layer.
  • Store data in a List<Employee> in memory (no real database needed).
  • Pre-populate with at least 3 seed employees (one of each type) in the constructor.
  • Implement: GetAll, GetById, Add.

Knowledge to use:

L12 — Repository Pattern · L11 — Clean Architecture
💡 Hints (try without first)
  • Infrastructure depends on Application (for the interface) — but Application does NOT depend on Infrastructure.
  • GetById should return null (or throw) if not found — your Service in CP3 already handles that case.
  • The point of in-memory here: you can swap it for a real database later without changing Application.
LevelCriterion
🟡 BeginnerRepository exists in Infrastructure. Implements the interface. Data stored somewhere.
🟢 CompetentUses List<Employee>. Seed data present. All three methods correctly implemented.
🔵 ProficientCan explain how this is swappable (e.g., to EF Core repo) without Application layer knowing. GetById handles missing gracefully.

API Controller — EmployeesController
L5 · L11 · L13 ~15 min

🎯 What to Build

  • Create EmployeesController in the API/Presentation layer.
  • Inject IEmployeeService via constructor (not the repository directly).
  • Expose these endpoints:
    • GET /api/employees — returns all employees.
    • GET /api/employees/{id} — returns one employee. Return 404 if not found.
    • POST /api/employees — accepts employee data and adds it. Return 201 on success.
  • Return appropriate HTTP status codes (200, 201, 404, 400).

Knowledge to use:

L5 — Web API Controllers · L11 — Presentation layer · L13 — API & Frontend
💡 Hints (try without first)
  • Controller talks to IEmployeeService, not IEmployeeRepository — Presentation should never skip layers.
  • Catch the exception from service's GetEmployee() and return NotFound() in the controller.
  • Use [FromBody] for POST, [FromRoute] for id — review L5 attribute routing.
LevelCriterion
🟡 BeginnerController exists with 3 endpoints. May inject repository instead of service.
🟢 CompetentInjects IEmployeeService. All 3 endpoints return correct status codes. GET/{id} returns 404 on miss.
🔵 ProficientCan explain why the controller should never talk to the repository directly. POST validates via service and returns 400 on bad input.

Unit Tests — 3 Cases
L8 ~20 min

🎯 What to Build

Write exactly 3 unit tests for EmployeeService. Use a fake/stub repository — not the real InMemoryEmployeeRepository.

  • Test 1: GetAllEmployees() returns all employees from the repository.
  • Test 2: GetEmployee(id) throws an exception when the employee is not found.
  • Test 3: AddEmployee() throws an exception when Name is empty or null.

Each test must follow the Arrange → Act → Assert pattern.

Knowledge to use:

L8 — Unit Testing & TDD · L7 — DIP (why interfaces make testing easy)
💡 Hints (try without first)
  • Create a FakeEmployeeRepository class that implements IEmployeeRepository with hardcoded test data.
  • This is possible because the Service depends on the interface — you can swap real for fake.
  • For exceptions: use the Assert method that checks a specific exception type is thrown.
  • No mocking library needed — a simple fake class is enough (L8 explains this).
